## Iteration 3 — KAN-10: Importar movimientos desde Gmail

### Starting state
All 10 iteration-2 features are complete (see prd_iteration_2.json / progress_iteration_2.txt). Full test suite: 257 API tests (Jest) + 199 client tests (Vitest) = 456 tests green. Both TypeScript builds clean.

The import pipeline already has everything downstream of "raw text": LLM extraction with registered payment-method matching, second-pass new-category suggestion, description sanitizer, store_context web enrichment, and deterministic parseAmount/amountSuspect reconciliation — all currently coupled to the OCR upload path in api/src/routes/import.ts.

### Goal
Import expense movements directly from bank notification emails (e.g. DAVIbank purchase alerts) in the user's Gmail, instead of screenshotting them and uploading the image.

### Design decisions
- Google OAuth 2.0 authorization-code flow with the `gmail.readonly` scope via `googleapis`; tokens stored server-side in a single-row `gmail_connection` table (single-user app); access-token refresh handled transparently by a `getGmailClient()` helper. New env vars: GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_REDIRECT_URI.
- Hybrid import model: a manual picker (browse emails → extract → review → confirm) plus an hourly background poller (in-process setInterval in the API, GMAIL_POLL_INTERVAL_MINUTES, catch-up tick on startup) that pre-extracts new matching emails into a `gmail_pending_imports` queue. The review invariant is unchanged either way: polling only fills the pending queue; nothing reaches `movements` without passing through the review table and an explicit confirm.
- Extraction happens at poll time (not lazily at review time) because volume is low — LLM cost is negligible and the notification can say "N movements pending" with real amounts. Notification is in-app only (nav badge + browser tab title prefix); OS/browser push deferred — it would require a service worker and adds little for a single-user app. Polling runs only while the API server is running.
- Candidate emails are scoped by user-configured sender addresses (`gmail_senders` table), each with an optional `subject_contains` phrase (e.g. 'Alerta de compra' — filters out OTPs/statements/marketing from the same bank address), plus a date range and an ad-hoc subject search in the picker. Filters compile to Gmail query syntax (`from:` / `subject:` / `after:` / `before:`) so Google filters server-side; noise never reaches the app.
- The OCR extraction path is refactored into a shared `extractMovementsFromText` helper; email bodies (text/plain preferred, HTML→text fallback, Subject/From/Date prepended) flow through the exact same enrichment pipeline as OCR text.
- Deduplication via a `gmail_imported_messages` log keyed (gmail_message_id, movement_id): confirm writes it in-transaction, listing marks logged emails as already imported, re-confirms 409. Log rows survive movement deletion (ON DELETE SET NULL) so a deleted movement's email is not silently re-offered.
- Multiple movements per email are legal (one statement email can contain several purchases); only ids imported by *earlier* confirms conflict.
- Time of day: new nullable `time` (Postgres `time`, no timezone — receipts state local wall-clock time) alongside the existing `date`, which remains the canonical grouping/filter column. Extracted from receipts/notifications when present, optional in the form, never required. Chosen over converting `date` to timestamptz to avoid rippling through every date filter and timezone semantics.
- Duplicate handling is two-layered: gmail_message_id dedup catches re-importing the same email (hard 409); a soft `possibleDuplicate` warning at review catches cross-source repeats (same store + amount + date, e.g. email import + receipt photo of the same purchase). The warning never blocks — identical same-day purchases are legitimate — and is suppressed when both movements carry differing times. No uniqueness constraint on movement contents, by design.
