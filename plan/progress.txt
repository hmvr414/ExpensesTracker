### Motivating example
A DAVIbank Visa Platinum notification email for a purchase at OPENROUTER, INC currently parses as:
- Description: "Visa Platinum transaction" (payment method leaked into the description)
- Category: unresolved ("No category")
- Payment method: not captured at all (no such field existed)

### Design decisions
- Payment methods are user-registered entities (cards with brand/variant/last4, plus cash/transfer), not a fixed enum — enables AI matching of "tarjeta Visa Platinum" to a registered card and per-method reports in future iterations.
- When no existing category matches, a second LLM pass suggests a new category word shown in an editable text field; confirming auto-creates the category (find-or-create, auto-assigned color).
- Description quality strategy (3 layers): (1) prompt rules + server-side sanitizer forbidding payment vocabulary, (2) the user's previous descriptions for the same store as prompt context, (3) one-time web enrichment per unknown store via OpenRouter's web search plugin (`:online` model suffix), cached in a `store_context` table. Google scraping rejected (ToS/brittle); Wikipedia rejected (poor merchant coverage).
- Amount separator ambiguity ("40,313" COP parsed as 40.313): the model returns both `rawAmountText` and a normalized `amount`; a deterministic `parseAmount` helper re-parses the raw text server-side with locale heuristics and wins on disagreement, flagging the row `amountSuspect` so the review UI shows a ⚠ verify hint.

Selected as highest priority: it is the documented next backlog item and the sole blocker for #6

detectedPaymentLabel / detectedBrand / paymentAiSuggested across api/ and client/ found only the

TDD: wrote api/src/__tests__/import-payment-detection.test.ts first (10 tests, 9 red), then
implemented. All changes are in api/src/routes/import.ts — API-only feature, no client changes.

Changes (POST /api/import/extract):
- Fetches all payment_methods (id, name, kind, brand, variant) before the AI call and embeds them
  in the extraction prompt as a JSON list.
- Prompt now asks for four extra per-movement fields: paymentMethodId (registered match),
  detectedPaymentLabel / detectedBrand / detectedVariant (card mentioned but unregistered), with
  explicit matching rules: match on brand + variant even when the registered name differs; all four
  null when there is no payment signal. Bilingual cues included (tarjeta, compra, débito, crédito,
  efectivo + English equivalents).
- Server-side defense: paymentMethodId is looked up in a Map of registered ids and nulled out when
  unknown (hallucination guard); normalizeBrand() maps free-text brands to the canonical enum
  (visa | mastercard | amex | other — e.g. 'VISA' → visa, 'Master Card' → mastercard, 'American
  Express' → amex, 'Diners Club' → other), null/empty stays null.
- Each movement in the extract response now carries paymentMethodId, paymentMethodName,
  detectedPaymentLabel, detectedBrand, detectedVariant, paymentAiSuggested (true only when a
  registered method was matched and validated). When a valid id is matched, detected* fields are
  forced to null even if the model also filled them. Nothing is persisted at extract time
  (verified by test); persistence stays in /confirm, which already accepts payment_method_id.

   server's { error } message (axios.isAxiosError) or a generic fallback in a per-row
